dpop-auth implements DPoP — Demonstration of Proof-of-Possession — for Node.js. Every access token is cryptographically bound to a private key held on the user’s device, and every request carries a fresh, single-use proof. Steal the token, and you still can’t use it.

Features

Everything a sender-constrained
API needs.

01

Device-Bound Tokens

Access tokens carry a confirmation claim (cnf/jkt) tying them to a public key generated on the device. A token without its matching private key fails verification.

02

RFC-Compliant DPoP Proofs

Short-lived proof JWTs (typ: dpop+jwt) signed per request with htm, htu, iat and jti claims — matching the DPoP draft specification.

03

Anti-Replay Protection

Every proof carries a unique JTI tracked in a replay store — memory and Redis backends included — so the same proof can never be accepted twice.

04

Anti-Scraping Layer

Scripts and scrapers can’t replay a captured token, because each request needs a fresh cryptographic signature from the device’s private key.

05

Fingerprint Binding

An optional device-fingerprint claim (fph) adds a second, behavioural layer on top of the cryptographic binding.

06

Express Middleware & TypeScript

Drop-in Express middleware, a secure refresh-token flow, full TypeScript definitions, and a comprehensive test suite — with only one runtime dependency: jose.

Why DPoP

Bearer JWT vs DPoP Auth

A bearer token — a normal JWT — authorises whoever bears it. That single property is behind most token-theft, replay and scraping attacks on APIs today.

Attack vector Traditional JWT DPoP Auth
Token theft × Token works anywhere ✓ Useless without the device key
Scraping / automation × Easy to automate ✓ Requires device binding
Replay attacks × Same token reusable ✓ Fresh proof per request
Device spoofing × No device binding ✓ Cryptographic binding
Man-in-the-middle × Token exposed ✓ Request-specific proofs
How it’s different

Not just another
JWT library.

01

Bearer by default vs proof by default

Popular libraries like jsonwebtoken or passport-jwt issue and verify bearer tokens — whoever holds the token owns the session. dpop-auth flips the model: possession of a string proves nothing; only a signature from the device’s private key does.

02

Full stack, not half the protocol

Most DPoP support in the wild is client-side only (e.g. inside OAuth libraries such as oauth4webapi). dpop-auth covers the whole flow server and client: key-pair generation, token creation and verification, proof creation and verification, replay stores, and a refresh-token flow bound to the same device key.

03

Scraping is a first-class threat model

Where other auth libraries stop at “is this token valid?”, dpop-auth treats automated abuse as an explicit target — fresh per-request proofs plus optional fingerprint binding make scripted scraping of your API impractical, not just unauthorised.

04

Batteries included, footprint minimal

Express middleware, Redis replay store, TypeScript definitions and 80%+ coverage thresholds ship in the box — while the whole library depends on a single runtime package, jose. No framework lock-in, no dependency sprawl.

Quick start

Protect a route in
ten lines.

01 · Server (Express)
import { dpopAuth } from 'dpop-auth';

app.use('/api/protected', dpopAuth({
  secret: process.env.DPOP_SECRET,
  enableFingerprinting: true,
}));
02 · Client (Browser)
const proof = await createDPoPProof(
  method, url, devicePrivateKey, devicePublicKey
);

await fetch(url, { headers: {
  'Authorization': `DPoP ${accessToken}`,
  'DPoP': proof,
}});
