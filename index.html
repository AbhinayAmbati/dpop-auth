Node.js · TypeScript · Apache-2.0 — v1.0.2

dpop-auth is a Node.js library that makes a stolen access token worthless. It implements DPoP — Demonstration of Proof-of-Possession — binding every token to a cryptographic key held on the user’s device, and requiring a fresh, single-use proof on every request.

A normal JWT is a bearer token: whoever holds it, owns the session. dpop-auth replaces that assumption with a cryptographic one — possession of a string proves nothing; only a signature from the device’s private key does. It ships with Express middleware, memory and Redis replay stores, a device-bound refresh flow, and full TypeScript definitions, in a package with a single runtime dependency.

The library implements the DPoP mechanism standardized in RFC 9449 and is covered by a test suite with an enforced 80% coverage threshold.

Security. Access tokens carry a confirmation claim (cnf/jkt) with the thumbprint of a public key generated on the device. Every API request is signed into a short-lived DPoP proof JWT — bound to the HTTP method, the target URI, and a single-use ID (jti) tracked in a replay store. A replayed proof is rejected; a replayed token is useless without the private key it was issued to.

Anti-scraping. Automation and scraping break against dpop-auth by construction: a script can copy a token out of a logged request or a compromised proxy, but it cannot forge an ES256 signature from a private key generated inside the user’s browser and never transmitted. An optional device-fingerprint claim (fph) adds a second, behavioural layer on top of the cryptography.

Developer experience. One middleware call protects a route. The package generates key pairs, issues and verifies tokens, creates and validates proofs, exposes memory and Redis replay stores, and includes optional-auth and requireDevice variants for partial protection. Everything is typed end to end in TypeScript.

Small footprint. The only runtime dependency is jose. There is no framework lock-in beyond Express support, no database requirement, and the whole flow works with the browser’s built-in WebCrypto API.

How it works

Four steps, one bound session.

The flow is symmetric: the server verifies exactly what the browser generates, and the same device key protects both the access token and the refresh token.

01

Generate device keys

At login, the browser generates an ES256 key pair with WebCrypto. The private key never leaves the device.

02

Issue a bound token

The server embeds the public key’s thumbprint (cnf/jkt) and an optional fingerprint hash into the token pair.

03

Sign every request

Each API call carries a DPoP proof JWT — signed by the private key, bound to the method, URI, and a unique jti.

04

Verify & enforce

The middleware checks the signature, the binding, the time window and the replay store — then lets the request through.

Features

Everything a sender-constrained API needs.

cnf

Device-bound tokens

Access tokens carry a confirmation claim (cnf/jkt) tying them to a public key generated on the device. A token without its matching private key fails verification.

jwt

RFC-compliant DPoP proofs

Short-lived proof JWTs (typ dpop+jwt) signed per request with htm, htu, iat and jti claims — following RFC 9449.

jti

Anti-replay protection

Every proof carries a unique JTI tracked in a replay store — memory and Redis backends included — so a proof can never be accepted twice.

fph

Anti-scraping layer

Scripts can’t replay a captured token: each request needs a fresh signature from a private key the scraper never had.

#

Fingerprint binding

An optional device-fingerprint claim (fph), derived from user-agent, language, screen and timezone signals, adds a second layer on top of the cryptography.

mw

Express middleware & TypeScript

Drop-in middleware (plus optional-auth and requireDevice variants), a device-bound refresh flow, and full TypeScript definitions built in.

Batteries included.

Quick start

Protect a route in ten lines.

Config knobs: algorithm (ES256/RS256), expiresIn (default 300s), clockTolerance, maxAge for replay windows, issuer/audience, and enableFingerprinting.

01 Server — Express
import { dpopAuth, MemoryReplayStore } from 'dpop-auth';

app.use('/api/protected', dpopAuth({
  secret: process.env.DPOP_SECRET,
  algorithm: 'ES256',
  expiresIn: 300,
  enableFingerprinting: true,
  replayStore: new MemoryReplayStore(),
}));

app.get('/api/protected/data', (req, res) => {
  // req.token.sub — the user
  // req.thumbprint — the device
  res.json({ user: req.token.sub, device: req.thumbprint });
});
02 Client — Browser
// once, at login:
const { publicKeyJwk } = await generateDeviceKeys();

// on every request:
const proof = await createDPoPProof(
  method, url, devicePrivateKey, publicKeyJwk
);

await fetch(url, { headers: {
  'Authorization': `DPoP ${accessToken}`,
  'DPoP': proof,
}});
